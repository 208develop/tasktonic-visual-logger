# TaskTonic Log Dictionary Analysis

This document provides a structured breakdown of the different types of log dictionaries generated by the TaskTonic framework. Understanding these variations is the first step to building a clean and robust `enrich_data` function for the UI.

The framework produces two main types of logs: **Session Logs** (global) and **Tonic Logs** (component-specific).

---

## 1. Session Log

This log establishes the global context of a logging session. It does **not** belong to any specific Tonic, and therefore **never contains an `id` field**.

#### Type: new session

Sent one time at the start of the app session.

- **Key Identifiers:** Contains `start_new_session: True`

- **Contents:**
  
  - `project` (str): The name of the running application.
  - `start@` (float): Unix timestamp of the session start.
  - `connection` (str): IP and port of the sender.
  - `logger_version` (int): Version of the logging protocol.

- **Example:**
  
  ```json
  {
  'start_new_session': True, 
  'project': 'Dummy log generator', 
  'start@': 1775756407.5013912, 
  'connection': '<ip>:<port>', 
  'logger_version': 0
  }
  ```

---

## 2. Tonic Log (Including Catalysts)

This is the standard log type emitted by any active component (Tonic or Catalyst) within the framework.

- **Required Base Fields:** Every Tonic log *always* begins with:
  - `id` (int): The unique identifier of the Tonic.
  - `start@` (float): Unix timestamp of the event.
  - `log` (list, optional): An array of strings containing application-specific text messages intended purely for display.
- **Optional Base Fields:**
  - `sparkle` (str): The name of the method being run (e.g., `'ttse__on_tm_make_noice'`).
  - `source` (str): What triggered this execution (e.g., `'tm_make_noice.expired'`).
  - `duration` (float, optional): Execution time in seconds.
- **Optional Application Data:**
  - `flags` (list): An array of strings containing debug flags (e.g., `['flag1', 'flag2']`). While the flags themselves are application-specific, the UI must process them. This can include specific styling directives like `'log_color_white'`.
- **State Dependency (`state` field):**
  - If a `state` field (int) is present at the root of the log, it indicates that the executed `sparkle` is a *state-dependent* method. The integer represents the currently active state index.

Depending on the action occurring within the Tonic, this base log is extended into specific sub-types:

### 2a. Execution Log

Represents a standard method execution.

- **Key Identifiers:** Contains `sparkle` and `source`.

- **Contents:**
  
  - `sparkle` (str): The name of the method being run.
  - `source` (str): What triggered this execution.
  - `duration` (float, optional): Execution time in seconds.

- **Example:**
  
  ```json
  {
  'id': 6, 
  'start@': 1775756419.1873615, 
  'log': ['Hé, pssst ........'], 
  'sparkle': 'ttse__on_tm_make_noice', 
  'source': 'tm_make_noice.expired', 
  'state': 0
  }
  ```

### 2b. System Logs (The `sys` field)

System logs extend the base Tonic Log with a `sys` dictionary containing framework-level state changes or initialization data.

#### Tonic Creation (Registration)

When a new Tonic is instantiated, the `sys` field contains its blueprint.

- **Key Identifiers:** `sys.created == True`.

- **Contents of `sys`:**
  
  - `name` (str): The assigned name (e.g., `'tt_log_service'`).
  - `base` (int): The ID of its parent/base Tonic (-1 means no base).
  - `type` (str): The class name.
  - `states` (list): Array of available state names. (The index here is used by future `state` integers).
  - `sparkles` (list): Array of available method names.

- **Example:**
  
  ```json
  {
  'id': 6, 
  'start@': 1775756417.5183458, 
  'log': [], 
  'sys': {
     'created': True, 
     'id': 6, 
     'name': '06.DummyStateGenerator', 
     'base': 2, 
     'type': 'DummyStateGenerator', 
     'states': ['be_quiet', 'noise', 'silent'], 
     'sparkles': ['_ttss__on_start', 'ttse__on_enter', '...']
     }
  }
  ```

#### State Change

Indicates that the Tonic has transitioned between states.

- **Key Identifiers:** The `sys` dictionary contains `state` (old) and `new_state` (new).

- *Note on mapping:* The integer values in `state` and `new_state` correspond to the index of the string in the `states` list provided during the Tonic's creation log.

- **Format:**
  
  - **Direct System Update:**
    
    ```json
    {
    'id': 1, 
    'start@': 1775756407.5063908, 
    'sys': {
       'state': -1, 
       'new_state': 1
       }
    }
    ```

### 2c. Teardown / Finish Log

When a Tonic completes its lifecycle and is removed from the Catalyst.

- **Key Identifiers:** Sparkle names related to completion (`ttsc__finish`, `_ttss__on_completion`, `_ttss__remove_tonic_from_catalyst`).

- **Example:**
  
  ```json
  {
  'id': 0, 
  'start@': 1775756427.5288773, 
  'log': [], 
  'sparkle': '_ttss__remove_tonic_from_catalyst', 
  'source': '02.Dummy._ttss__on_completion'
  }
  ```

---

## Recommendations for the `enrich_data` function

To build a clean parser, your `enrich_data` function should route the dictionary based on this updated hierarchy:

1. **Check for Session Log:** `if 'id' not in log:`
   
   - If `log.get('start_new_session')`: Reset UI, store project name and start time.
   - *Return early, as this log does not belong to a Tonic.*

2. **Process Base Data & Styling:** - Extract `id`, `start@`, and `log` (for display).
   
   - **Process Flags:** Check `if 'flags' in log:`. Parse the array to extract UI directives (e.g., looking for strings like `'log_color_white'`) and store other flags for debug tooltips or visual badges.

3. **Check for System Events (`sys`):** `if 'sys' in log:`
   
   - *Creation (`log['sys'].get('created')`):* Register the new ID in your central lookup table. Crucially, save the `states` list so you can translate future state integers into readable strings.
   - *State Change (`'new_state' in log['sys']`):* Look up the new string name using the saved `states` list and update the visual state indicator for this specific ID.

4. **Process Execution Context (Optional Base Fields):** - If `sparkle` and `source` are present, format them for the UI header (e.g., `sparkle <- called by: source`).
   
   - Categorize the execution: Check if the `sparkle` starts with `_ttss` (System Sparkle) or `ttse`/`ttsc` (User Sparkle) to apply appropriate visual filtering or background colors.
   - If `state` is present at the root, append the string equivalent (looked up from step 3) to the display to indicate the state-dependency of the execution.

5. **Teardown check:**
   
   - If the `sparkle` indicates a completion action (e.g., `_ttss__remove_tonic_from_catalyst`), mark the Tonic as finished in the UI history.
