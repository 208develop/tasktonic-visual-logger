# TaskTonic Visual Logger Requirements

This document provides a structured breakdown of the different types of log dictionaries generated by the TaskTonic framework, along with the mandatory visual formatting rules for the UI. The goal is to provide a highly readable, consistent, and easily scannable event timeline.

---

## 1. General Formatting Rules

All logs share a common baseline layout. The primary line identifies the event, followed by optional content lines.

### 1.1 Common Prefix

Every rendered log line must begin with the timestamp and the identification of the Tonic that generated it:
`[HH:MM:SS.mmm] <id> <name>`

### 1.2 Visual Markers (Badges/Icons)

To quickly scan the timeline for crucial lifecycle events, specific log types must include a visual marker 
(e.g., an icon, a colored badge, or a bold prefix) immediately before the log text.

* **[SESSION]** : Session-level events (start, end, configuration changes).
* **[CREATE]** : Instantiation of a new Tonic.
* **[STATE]** : A transition from one state to another.
* **[FINISH]** : A Tonic is removed and destroyed.

### 1.3 Visual Call Tracing (Source Lines)

To visually represent the execution flow and dependencies, a colored line must connect the caller's ID lane to the 
executed log's lane. This line is drawn just above the log block.

* **External Calls:** A horizontal line starts from the caller's vertical lane. The line must be rendered in the 
  **caller's assigned theme color**. It runs horizontally towards the executing tonic's lane and terminates by 
  angling downwards at 45 degrees directly into the executing tonic's circular lane marker (the dot).
* **Internal (Self) Calls:** If a tonic calls its own sparkle, the line starts from the tonic's lane, extends 
  horizontally outward by a short distance, and loops back down at a 45-degree angle into the new dot, visually 
  indicating a recursive or internal trigger.

## 2. Event Types & Layouts

### 2.1 The Standard Sparkle Execution

The most common log type, representing a standard or state-dependent method call.

**Format:**
`[time] <id> <name>[<state>] . <sparkle_name>  <--  <source_id> <source_name>[<source_state>] . <source_sparkle>`

* *Note 1: The `[<state>]` block is ONLY rendered if the executed sparkle is state-dependent.*
* *Note 2: The `[<source_state>]` block is ONLY rendered if the calling source was in a specific state.*
* *Note 3: The `source` block is only rendered if a caller is present.*

**Data Payload:**
If the log dictionary contains a `log` array (custom text messages or flags), these lines are rendered beneath 
the main header, slightly indented.

**Example:**
`[14:05:22.105] 06 DummyStateGenerator[noise] . ttse__on_tm_make_noice  <--  02 Dummy[idle] . tm_make_noice.expired`
`    Hé, pssst ........`
`    Flags: {'debug': True}`

### 2.2 State Transition

Indicates a Tonic has moved to a new state within its state machine.

**Format:**
`[time] <id> <name>  [STATE]  STATE TO [<new_state>] (from [<old_state>])`

**Example:**
`[14:05:22.555] 06 DummyStateGenerator  [STATE]  STATE TO [silent] (from [noise])`

### 2.3 Tonic Creation

Indicates a new component has been registered in the Catalyst.

**Format:**
`[time] <id> <name>  [CREATE]  Initialized as <type> (Base: <base_id>)`

**Data Payload:**
The creation log must list the available states and sparkles beneath the header.

**Example:**
`[14:05:22.001] 06 DummyStateGenerator  [CREATE]  Initialized as DummyStateGenerator (Base: 02)`
`    States: ['be_quiet', 'noise', 'silent']`
`    Sparkles: ['_ttss__on_start', 'ttse__on_enter', 'ttsc__finish', ...]`

### 2.4 Tonic Finish / Teardown

Indicates a component has completed its lifecycle and is removed.

**Format:**
`[time] <id> <name>  [FINISH]  Removed from Catalyst`

**Data Payload:**
Any closing messages generated by the system (e.g., remaining tonics list).

**Example:**
`[14:05:27.529] 06 DummyStateGenerator  [FINISH]  Removed from Catalyst`
`    Tonic 6 has been removed from Catalyst. (left [7])`

### 2.5 Session Logs

Events that dictate the flow of the entire application, not tied to a specific ID.

**Format:**
`[time] -- SESSION --  [SESSION]  <Event Description>`

**Example:**
`[14:05:20.000] -- SESSION --  [SESSION]  New Session Started: 'Dummy log generator' (v1.0)`
`    Connection: 127.0.0.1:5829`

## 3. Log Dictionary Mapping (The `enrich_data` logic)

The framework produces two main types of logs: **Session Logs** (global) and **Tonic Logs** (component-specific). 
To build a clean parser, the `enrich_data` function should route the dictionary based on this hierarchy:

### 3.1 Check for Session Log

`if 'id' not in log:`

* If `log.get('start_new_session')`: Reset UI, store project name and start time.
* *Return early, as this log does not belong to a Tonic.*

### 3.2 Process Base Data & Styling

Extract `id`, `start@`, and `log` (for display).

* **Process Flags:** Check `if 'flags' in log:`. Parse the array to extract UI directives 
  (e.g., looking for strings like `'log_color_white'`) and store other flags for debug tooltips or visual badges.

### 3.3 Check for System Events (`sys`)

`if 'sys' in log:`

* **Creation (`log['sys'].get('created')`):** Register the new ID in your central lookup table. Crucially, 
  save the `states` list so you can translate future state integers into readable strings.
* **State Change (`'new_state' in log['sys']`):** Look up the new string name using the saved `states` list 
  and update the visual state indicator for this specific ID.

### 3.4 Process Execution Context (Optional Base Fields)

* If `sparkle` and `source` are present, format them for the UI header (e.g., `sparkle <-- called by: source`).
* Categorize the execution: Check if the `sparkle` starts with `_ttss` (System Sparkle) or `ttse`/`ttsc` (User Sparkle) 
  to apply appropriate visual filtering or background colors.
* If `state` is present at the root, append the string equivalent (looked up from step 3.3) to the display to 
  indicate the state-dependency of the execution.

### 3.5 Teardown Check

* If the `sparkle` indicates a completion action (e.g., `_ttss__remove_tonic_from_catalyst`), mark the Tonic as 
  finished in the UI history.

## 4. Required Framework Updates

To achieve the layout described above, the TaskTonic framework's internal logging mechanism needs the following 
enhancements:

### 4.1 Enrich the `source` field

Currently, the `source` field is often a simple string. To draw the visual call tracing lines (Section 1.3), 
the UI needs exact caller ID coordinates.
**Requirement:** When a sparkle is triggered by another Tonic, the framework must pass a structured `caller` dictionary.

```json
"caller": {
    "id": 2,
    "name": "Dummy",
    "state_idx": 0, 
    "sparkle": "tm_make_noice.expired"
}
```

### 4.2 Standardize Timer Sources

If a sparkle is triggered by a timer (e.g., `tm_make_noice.expired`), there is technically no "calling Tonic ID" 
other than the Tonic itself that owns the timer.
**Requirement:** In the format `[time]<id> <name> . <sparkle> <-- <source>`, if the source is just a timer, 
render it simply as `<-- Timer: tm_make_noice`. The visual line should be drawn as an internal (self) call.

### 4.3 Dedicated Teardown Flag

**Requirement:** Add a simple boolean flag `sys.destroyed: True` to the final log dictionary of a Tonic, mirroring 
the `sys.created: True` flag. This makes the `[FINISH]` parsing 100% reliable without relying on string matching.
